# 画面の書き方

Expo アプリの画面の書き方のルール。置き場は[フォルダ構成](./フォルダ構成.md)、使うライブラリは[選定ライブラリ](./選定ライブラリ.md)が持つ。本資料は「画面をどう書くか」を扱う。

## データ取得を伴う画面の 4 状態

データを取得する画面は、**Loading・Error・Empty・Data** の 4 状態を必ず扱う。

| 状態    | 条件                         | 表示                               |
| ------- | ---------------------------- | ---------------------------------- |
| Loading | 初回で、まだデータがない     | `Loading`                          |
| Error   | 取得に失敗した               | `ErrorView`（メッセージと再試行）  |
| Empty   | 取得は成功したが、データが空 | `EmptyView`（文言を props で渡す） |
| Data    | データがある                 | 画面本体                           |

* 判定の順序は、Loading → Error → Empty → Data。早期 return で書く。
* **hook は、早期 return より前に呼ぶ。** hook は条件分岐の中で呼べないため、早期 return の後に hook を置かない。
* 再取得中でデータがすでにあるときは、Loading に戻さず、データを表示する（TanStack Query の `isPending` は、データがまだない初回だけ true になる）。

```tsx
export function ItemList() {
  const { data, isPending, error, refetch } = useGetItems()

  if (isPending) return <Loading />
  if (error) return <ErrorView message={error.message} onRetry={refetch} />
  if (data.length === 0) return <EmptyView message='商品がありません' />

  return <ItemListView items={data} />
}
```

* `error.message` が使えるのは、mutator が `ErrorType` を export してエラーの型を上書きしているため（[選定ライブラリ](./選定ライブラリ.md#エラーの型)）。上書きしないと、エラーの型が `unknown` になり、型エラーになる。

### 画面の一部だけが状態に依存するとき

一覧の挨拶やフィルタのように、常に出したい部分があるときは、画面全体を早期 return で置き換えられない（ヘッダーとフィルタが消える）。**状態に依存する部分を別のコンポーネントに分け**、そこで早期 return する。親の画面は、hook を呼んで固定部分を描く。

```tsx
export function PostList() {
  const { data, isPending, error, refetch } = useSearchPosts()
  return (
    <View>
      <PostListHeader />
      <PostListBody data={data} isPending={isPending} error={error} onRetry={refetch} />
    </View>
  )
}

function PostListBody({ data, isPending, error, onRetry }: Props) {
  if (isPending) return <Loading />
  if (error) return <ErrorView message={error.message} onRetry={onRetry} />
  if (!data || data.posts.length === 0) return <EmptyView message='投稿がありません' />
  return <FlatList data={data.posts} … />
}
```

* `data` の型は、生成された型（`PostList`）を使う。手で書き直さない。一覧の API が、配列でなくオブジェクト（`{ posts, total, … }`）を返すときは、画面で `data.posts` を使う。

### 1 件の取得

1 件を取得する画面（詳細、編集）に、Empty はない（取得が成功すれば、データがある）。Loading・Error・Data の 3 状態で書く。存在しない ID は 404 になるので、Error として扱い、再試行を出す。

### 取得が別の取得に依存するとき

ログイン中のユーザーの ID で一覧を取るように、取得が別の取得の結果に依存するときは、`enabled` で後の取得を止め、前の取得が済むまで待つ。

* `enabled: false` の取得は、データがないので、`isPending` が true のままになる。前の取得が**失敗**すると、「読み込み中」のまま止まる。
* 前の取得の `error` を優先して返す合成 hook（feature の `hooks/`）にまとめ、画面は、その `isPending`・`error`・`refetch` で 4 状態を書く。

```tsx
// src/features/items/hooks/use-my-items.ts
export function useMyItems() {
  const user = useCurrentUser()
  const userId = user.data?.id
  const items = useListUserItems(userId ?? 0, {
    query: { enabled: userId !== undefined, select: (result) => result.items }
  })

  const error = user.error ?? items.error
  return {
    data: items.data,
    isPending: !error && (user.isPending || items.isPending),
    error,
    refetch: () => (user.error ? user.refetch() : items.refetch())
  }
}
```

### 共通コンポーネント

`src/components/screen-state/` に、1 ファイル 1 コンポーネントで置く。

| ファイル         | props                | 役割                           |
| ---------------- | -------------------- | ------------------------------ |
| `loading.tsx`    | なし                 | 読み込み中の表示               |
| `error-view.tsx` | `message`、`onRetry` | エラーメッセージと再試行ボタン |
| `empty-view.tsx` | `message`            | データが空のときの表示         |

## フォーム

検証を伴う入力フォームは、React Hook Form と Zod で書く（採用理由は[選定ライブラリ](./選定ライブラリ.md#フォームreact-hook-form--zod)）。検証のない単純な入力は、`useState` でよい。

* **スキーマは feature の `schemas/` に置く。** 純粋なロジックなので、単体テストの対象になる（画面のファイルに書くと、`react-native` を import するため、単体テストができない）。型は `z.infer` で取る。
* 入力は `Controller` で `TextInput` に接続する。エラー表示つきの共通入力コンポーネント `text-field.tsx` を `src/components/form/` に置き、各フォームはそれを使う。
* パスワードの入力は `secureTextEntry`、ユーザー名やメールアドレスは `autoCapitalize='none'` を、`TextField` の props で渡す。ログイン画面（`features/auth/screens/login.tsx`）が見本。
* 送信中は二重送信を防ぐ。`formState.isSubmitting` を使い、送信ボタンを無効にする。
* 送信の失敗は、`try/catch` で受け、エラーを表示して、前の画面へは戻らない（握らないと、未処理の例外になる）。
* フォームの項目と API の本文は、一致しないことが多い。変換は、`schemas/` の純粋な関数に置く（`toNewItem` など）。配列の項目（タグなど）は、1 つの文字列（カンマ区切り）をフォームの値にし、配列への変換と検証（個数の上限、重複の除去）を `schemas/` の関数で行う。`useFieldArray` は、項目ごとに入力欄が要るときだけ使う。
* `Pressable` の `onPress` に `handleSubmit(onSubmit)` をそのまま渡すと、イベントの型が合わず型エラーになる。`() => handleSubmit(onSubmit)()` と関数で包む。

```tsx
// src/features/items/schemas/item-form.ts
export const itemFormSchema = z.object({
  name: z.string().min(1, '名前を入力してください')
})
export type ItemFormValues = z.infer<typeof itemFormSchema>
```

```tsx
// src/features/items/screens/item-create.tsx
const { control, handleSubmit, formState } = useForm<ItemFormValues>({
  resolver: zodResolver(itemFormSchema),
  defaultValues: { name: '' }
})

<Controller
  control={control}
  name='name'
  render={({ field, fieldState }) => (
    <TextField
      value={field.value}
      onChangeText={field.onChange}
      onBlur={field.onBlur}
      error={fieldState.error?.message}
    />
  )}
/>
<Pressable
  accessibilityRole='button'
  disabled={formState.isSubmitting}
  onPress={() => handleSubmit(onSubmit)()}
>
  <Text>登録</Text>
</Pressable>
```

### 作成と編集で同じフォームを使うとき

編集のフォームは、取得したデータを初期値にする。`useForm` の `defaultValues` は初回の値で固定されるので、取得が済んでからフォームを描く。

* **取得（4 状態）を持つ画面と、フォーム本体を分ける。** 画面（`item-edit.tsx`）が取得して Loading・Error を処理し、データが揃ってからフォーム本体（`components/item-form.tsx`）を、初期値つきで描く。作成の画面は、空の初期値で同じフォーム本体を描く。
* フォーム本体は、送信の処理（`onSubmit`）と初期値を props で受ける。入力中に離れるときの確認（次の節）も、フォーム本体が持つ。

## 一覧の描画

`ScrollView` は、中身をすべて一度に描画する。`FlatList` は、見えている範囲だけを描画する（仮想化）。件数に応じて使い分ける。

| 一覧の件数 | 使うもの |
| --- | --- |
| 少なく、上限が決まっている（数十件まで） | `ScrollView` |
| 増えうる、または上限がない | `FlatList` |
| 非常に多く、`FlatList` で滑らかに動かない | `@shopify/flash-list` を検討する |

* 迷ったら `FlatList` を選ぶ。件数が少ないうちは差が出ないが、増えたときに書き換えずに済む。
* **`FlatList` の行に最大幅をつけて中央に寄せるときは、行に `CONTENT_WIDTH`（`w-full max-w-… self-center`）を付ける。`contentContainerClassName` に `items-center` は付けない。** `FlatList` は、各行を `View`（セル）で包むので、`items-center` を付けると、そのセルが内容の幅に縮み、行の幅がばらばらになる。
* 縦の `ScrollView` の中に、縦の `FlatList` を置かない（仮想化が効かなくなる）。一覧の上に固定の部分（ヘッダーなど）があるときは、`View` に並べるか、スクロールさせたいなら `FlatList` の `ListHeaderComponent` に渡す。

## ダイアログ

確認と案内のダイアログは、`src/components/dialog/dialog.tsx` の `Dialog` を使う。`Alert.alert` は、ネイティブでは動くが、Web（react-native-web）では何も起きないので使わない。

```tsx
<Dialog
  visible={open}
  title='削除しますか？'
  message='この操作は取り消せません。'
  confirmLabel='削除する'
  onConfirm={remove}
  cancelLabel='キャンセル'
  onCancel={() => setOpen(false)}
  destructive
/>
```

* `cancelLabel` を渡さなければ、確認ボタンだけの「案内」になる。
* `destructive` は、取り消せない操作のときに付ける（確認ボタンが警告の色になる）。
* `busy` は、確認の処理中に付ける（確認ボタンを押せなくして、二重に実行されないようにする）。
* 枠の外をタップしても閉じない（目的が確認なので）。Android の戻るボタンは、キャンセル（なければ確認）として扱う。
* **Esc キーで閉じる、フォーカスをダイアログの中に留める、といった Web のアクセシビリティには対応していない。** 必要なアプリが足す。

### 入力中に画面を離れるとき

入力があるまま画面を離れようとしたら、`usePreventRemove` で離れるのを保留し、`Dialog` で確認する。

```tsx
const [leave, setLeave] = useState<{ repeat: () => void } | null>(null)
const [allowLeave, setAllowLeave] = useState(false)
const disablePrevention = usePreventRemove(
  formState.isDirty && !allowLeave,
  ({ repeat }) => setLeave({ repeat })
)

// 送信に成功したら、確認なしで離れる
const onSubmit = async (values) => {
  try {
    await mutateAsync(values)
  } catch {
    return // 失敗は、エラー表示で伝える。前の画面へは戻らない
  }
  disablePrevention()
  router.back()
}

// 「破棄する」: 保留を解いて、保留した操作をもう一度行う
const discard = () => {
  setAllowLeave(true)
  leave?.repeat()
  setLeave(null)
}
```

* `usePreventRemove` は `expo-router` から import する。Web では、ブラウザのタブを閉じる操作も保留される。
* `useNavigation().addListener('beforeRemove', …)` は、この版の型では使えない（`beforeRemove` が型に無い）ので、`usePreventRemove` を使う。

## セーフエリアとキーボード

### セーフエリア

* ノッチ、ホームインジケータ、Android のナビゲーションバーに内容が隠れないようにするには、`react-native-safe-area-context` を使う（Expo Router の peer 依存として入っている）。
* **画面は、`src/components/layout/screen.tsx` の `Screen` で包む。** `Screen` は、`react-native-safe-area-context` の `SafeAreaView` で、既定では下・左・右に余白を足す。上側は、ヘッダーが持つ（Stack のヘッダー、Tabs のヘッダー）。
* **画面の内容は、`src/components/layout/content.tsx` の `Content` で包む。** 最大幅をつけて中央に寄せる（Web で広げても、横へ伸びきらない。幅の考え方は[選定ライブラリ](./選定ライブラリ.md#ブレークポイント)）。`ScrollView` の中身は、`contentContainerClassName='items-center'` にして、その中に `Content` を置く。`FlatList` は上の「一覧の描画」を見る。
* ヘッダーのない画面（全画面の表示など）は、`edges` に `'top'` を足す: `<Screen edges={['top', 'bottom', 'left', 'right']}>`。
* タブバーの上に描かれる画面でも、`Screen` を使ってよい。`SafeAreaView` は、実際にセーフエリアと重なる分だけを余白にするので、タブバーの分と二重にならない。
* ナビゲーション（Stack・Tabs）は、**下側の余白を持たない**（上側はヘッダーが持つ）。ヘッダーだけの Stack の画面を、そのまま描くと、一番下の内容が、ホームインジケータやナビゲーションバーと重なる。
* 余白だけを個別に足したいときは、`useSafeAreaInsets` を使う。
* Web では、CSS の `env(safe-area-inset-*)` を使う。Expo SDK 58 以降の Expo Router は、Web ではセーフエリアの自動計測をしないので、`SafeAreaProvider` を自分で足さない。

### ヘッダー（iOS 26 以降）

* iOS 26 以降（Liquid Glass）では、Stack のヘッダーが**既定で透明**になり、画面の内容がヘッダーの下に入って、上の部分が隠れる（`headerTransparent` の既定が iOS で `true` になるため）。Android とも見た目が違ってしまう。
* **従来の不透明なヘッダーにするには、ルートの `_layout.tsx` の `Stack` に `headerTransparent: false` を指定する**。ヘッダーの色は、ナビゲーションのテーマ（`src/theme.ts`）から決まる。
* iOS 26 以降の標準の戻るボタンは、Liquid Glass（ガラスの丸い背景）で描かれ、長押しすると遷移元のルートグループ名（`(tabs)`）のメニューが出る。Android と同じ見た目・動きにするため、ルートの `Stack` の `unstable_headerLeftItems` に、`src/components/layout/back-button.tsx` の `BackButton`（矢印のアイコン）を `hidesSharedBackground: true`（ガラスの背景を外す）で渡している。Android は標準の戻るボタンのまま。スワイプで戻る操作と、`usePreventRemove` による離脱の確認は、そのまま効く。
* `unstable_` の API なので、`expo-router` を上げたときは、戻るボタンの見た目と動きを見直す。

### キーボード

* 入力フォームの `ScrollView` には、`automaticallyAdjustKeyboardInsets`（iOS で、キーボードの分だけ余白を足す）と `keyboardShouldPersistTaps='handled'`（キーボードを出したまま、ボタンを 1 回のタップで押せる）を付ける。
* Android は、`app.json` の `android.softwareKeyboardLayoutMode`（既定は `resize`）で、キーボードが出たときのレイアウトが決まる。ステータスバーを半透明にしていると乱れるので、そのときは `KeyboardAvoidingView` で調整する。

## メモ化

`experiments.reactCompiler` を有効にしているため（[開発環境と設定](./開発環境と設定.md#appjson-の既定)）、**`useCallback`・`useMemo`・`React.memo` は書かない。** React Compiler が自動でメモ化する。

* 対象は関数コンポーネントのアプリのコード。クラスコンポーネントは最適化されない。
* 最適化を外したいコンポーネントやファイルには、`'use no memo'` ディレクティブを書く。
