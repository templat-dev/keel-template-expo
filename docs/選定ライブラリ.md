## アイコン（@expo/vector-icons）

* `@expo/vector-icons` は、`npx expo install @expo/vector-icons expo-font` で入れる（`expo-font` は peer 依存。`app.json` の `plugins` に `expo-font` が自動で足される）。
* タブのアイコンの例:

```tsx
import Ionicons from '@expo/vector-icons/Ionicons'

<Tabs.Screen
  name='index'
  options={{
    title: 'ホーム',
    tabBarIcon: ({ color, size }) => (
      <Ionicons name='home-outline' color={color as string} size={size} />
    )
  }}
/>
```

* `tabBarIcon` の `color` は `ColorValue`（数値や null を含む）で、Ionicons の `color`（`string`）と型が合わない。実際に渡るのは文字列なので、`as string` で渡す。

## スタイル（NativeWind）

### 採用理由と版

* Tailwind の `className` で書く。利用者が最も多い（週間ダウンロード数は約 128 万。Uniwind は約 62 万、2026 年 10 月時点）。Expo の公式ドキュメントも、Tailwind を使うなら NativeWind か Uniwind を挙げている。
* **安定版の 4.2.7（Tailwind CSS v3 系）を使う。** NativeWind v5 は 2026 年 10 月時点で RC（`5.0.0-rc.0`）で、Tailwind v4 に対応する。v5 が安定したら移行を検討する。Tailwind v4 を使いたいアプリは、Uniwind（Expo 専用、Tailwind v4 のみ）という選択肢もある。

### 入れ方

```bash
npx expo install react-native-reanimated react-native-worklets react-native-safe-area-context
npm install nativewind@4.2.7
npm install --save-dev tailwindcss@^3.4.17 prettier-plugin-tailwindcss@^0.5.11
```

設定ファイルは、リポジトリ直下に `tailwind.config.js`（`presets: [require('nativewind/preset')]`、`content` は `./src/**/*.{ts,tsx}`）、`babel.config.js`（`jsxImportSource: 'nativewind'` と `nativewind/babel`）、`metro.config.js`（`withNativeWind(config, { input: './src/global.css' })`）、`nativewind-env.d.ts`（`/// <reference types="nativewind/types" />`）を置く。`src/global.css` に Tailwind の 3 行（`@tailwind base` など）を書き、ルートの `_layout.tsx` の先頭で `import '../global.css'` する。`tsconfig.json` の `include` に `nativewind-env.d.ts` を足す。

`prettier-plugin-tailwindcss` は、`.prettierrc` の `plugins` に足し、`className` の並びを Tailwind 公式の順に整える。

### 書き方

* `StyleSheet` は使わず、`className` で書く。`ScrollView` の中身には `contentContainerClassName` を使う。
* 条件で変わるクラスは、テンプレートリテラルで組み立てる。
* `className` で書けない指定（複数行の入力の `textAlignVertical` など）だけ、`style` に書く。

### ダークモード

* **ネイティブでは、`expo-router` の `Link` に `className` を直接付けると、`dark:` のクラスが効かない**（レイアウトや `light` の色は効くが、ダークの色だけ適用されない）。`Link` には `asChild` を付け、中の `Pressable` / `Text` に `className` を書く。

```tsx
<Link href='/posts/new' asChild>
  <Pressable accessibilityRole='link'>
    <Text className='text-sky-700 dark:text-sky-400'>投稿する</Text>
  </Pressable>
</Link>
```

* iOS 27 のシミュレータで、ライトとダークの両方を確認した。アプリの起動中に端末のライト / ダークを切り替えても、画面に反映されなかった（再起動すると反映される）。原因は調べていない。

* `tailwind.config.js` で `darkMode: 'class'` にする。既定の `media` だと、**Web の開発サーバーで、起動のたびに「Cannot manually set color scheme, as dark mode is type 'media'」という例外が出る**（NativeWind 4.2.7 で確認。開発サーバーではスタイルシートが JS より後に挿入され、そのとき NativeWind が `media` のまま色スキームを設定しようとする）。
* `class` にすると、`dark:` のクラスは端末の設定に自動では従わない。ルートの `_layout.tsx` で、端末の設定を NativeWind に渡す。Web では、`html` に `dark` クラスを自分で付ける（付けないと、ダークの端末で文字が暗いままになる）。
* ヘッダー、タブバー、画面の背景は、ナビゲーションのテーマ（`ThemeProvider`）で、ライト / ダークに合わせる。

```tsx
// src/app/_layout.tsx（抜粋）
const colorScheme = useColorScheme() // react-native
const { setColorScheme } = useNativeWindColorScheme() // nativewind

useEffect(() => {
  const scheme = colorScheme === 'dark' ? 'dark' : 'light'
  setColorScheme(scheme)
  if (Platform.OS === 'web') {
    document.documentElement.classList.toggle('dark', scheme === 'dark')
  }
}, [colorScheme, setColorScheme])

return (
  <ThemeProvider value={colorScheme === 'dark' ? DarkTheme : DefaultTheme}>
    …
  </ThemeProvider>
)
```

### ブレークポイント

* `sm:`・`md:`・`lg:` などのブレークポイントは、画面の幅に応じた見た目の調整（余白、列の数、最大幅）に使う。既定の値は、主に Web 向けに設計されたもので、**ネイティブでも幅に応じて効く**（タブレットでは `md:`・`lg:` が効くことがある）。
* 「PC か、スマートフォンか」のような端末の種類の判定には使わない。タブレットで、PC 向けの見た目が混ざる。端末の種類で見た目を分ける必要があるアプリは、判定を 1 つの hook（`src/hooks/`）に閉じ込め、画面ごとに `useWindowDimensions` で分岐を書かない。

### 注意

* `app.json` の `web.output` は `"single"` のままにする。`"static"` にすると、開発サーバーが画面をサーバー側で描画し、AsyncStorage を使う Jotai の atom（`useDisplayName`）の箇所でエラーになった。

## 画像（expo-image）

画像を表示するアプリは、`expo-image` を使う（`npx expo install expo-image`。テンプレートには入れていない）。

* ディスクとメモリのキャッシュ（`cachePolicy`、既定は `disk`）、読み込み中のプレースホルダ（`placeholder`。blurhash も使える）、切り替えの `transition` を持つ。Web にも対応している。
* 寸法は `style` で指定する。`className`（NativeWind）で書けるかは、公式ドキュメントに記載がない。使うときに確かめる（サードパーティの部品は、NativeWind の `cssInterop` で `className` と対応づける必要がある場合がある）。

### テーマ（`src/theme.ts`）

JS で色の値が要る場所（ナビゲーションのテーマ、タブバーの色、`ActivityIndicator` など）は、`src/theme.ts` の色の定義（ライト / ダーク）を使う。`className` で書ける場所は、Tailwind の色を使う。

* `src/theme.ts`: `lightColors` / `darkColors`（背景、面、文字、境界線、主色、警告色）と、ナビゲーションのテーマ（`navigationTheme(isDark)`）。**アプリごとに、ここの値を書き換える。**
* `src/hooks/use-theme.ts`: 端末のライト / ダークに合わせた色を返す `useTheme()`。
* ルートの `_layout.tsx` が、`navigationTheme` を `ThemeProvider` に渡す。ヘッダー、タブバー、画面の背景の色が、ここから決まる。
* 同じ色が JS と `className` の両方に出ないよう、`theme.ts` の各値に、対応する Tailwind の色をコメントで添えている（例: `primary: '#0369a1' // sky-700`）。色を変えるときは、両方を合わせる。

## クライアント状態（Jotai）

サーバーの状態は TanStack Query が持つ。Jotai が持つのは、それ以外の状態（認証ユーザー、入力途中の下書き、UI の一時状態など）。

* Provider は置かない。Provider なしで使うと既定のストアが使われる。
* React Context は、変化の少ない値（テーマ・ロケールなど）と、ライブラリが要求する Provider（`QueryClientProvider` など）に限る。変化の多い値には使わない。
* atom の置き場は、専用のフォルダを作らず、使うファイルに直接書いてよい（[フォルダ構成](./フォルダ構成.md#3-昇格ルール共通フォルダへの移動)）。
* React の外（mutator など）から読み書きするときは、`getDefaultStore()` で取った既定のストアに `get` / `set` する。たとえば、API が 401 を返したときに、mutator が認証状態の atom を未ログインへ戻せる。
* 永続化は `atomWithStorage` を使う。React Native では `createJSONStorage` に AsyncStorage を渡す。AsyncStorage は非同期なので、atom の値は Promise になり、現在の値を見て更新するときは `await` が要る。
* **認証トークンなど秘密の値は、`atomWithStorage`（AsyncStorage）に入れない。** 保存先の規約は[認証](./認証.md)が持つ。

## フォーム（React Hook Form + Zod）

検証を伴う入力フォームは、React Hook Form（RHF）と Zod で書く。検証のない単純な入力は、`useState` でよい。

* RHF は React Native でも使える。入力は `Controller` でラップし、`field` の `onChange` / `onBlur` / `value` を `TextInput` の `onChangeText` / `onBlur` / `value` に接続する。
* 検証のスキーマは Zod で定義し、`@hookform/resolvers` の `zodResolver` を `useForm` の `resolver` に渡す。型は `z.infer` で取る。
* `@hookform/resolvers` は 5 系を使う（`npm install @hookform/resolvers@5`。サンプルは 5.9.2）。最新の 6.0.0 は、optional な peer 依存の `effect` が競合して、`npm install` が ERESOLVE で止まる（2026 年 10 月時点）。Zod v4 を使うときは、3.10 以上が必要で、`tsconfig.json` の `moduleResolution` を `"bundler"`・`"node16"`・`"nodenext"` のいずれかにする（合わないと `Cannot find module '@hookform/resolvers/zod'` になる）。
* Orval の Zod 生成（`client: 'zod'`）は、テンプレートでは使わない。フォームの項目は API のリクエスト本文と一致しないことが多く、フォーム専用のスキーマのほうが素直なため。一致するアプリが、必要なら足す。

## API クライアントの生成（Orval）

### 役割

* `src/api/openapi.yaml` から、型・API 呼び出し関数・TanStack Query の hook を生成する。契約をバックエンドと共有するアプリは、`orval.config.ts` の入力パスを共有の場所に向けてよい。
* 通信ライブラリではない。通信は標準の `fetch` で行い、認証ヘッダと 401 処理は mutator（`src/api/mutator.ts`）に集約する。
* 生成物は `src/api/generated/` に置く。**手で編集しない。** 型が合わないときは OpenAPI 契約を直して再生成する。
* 設定ファイル（`orval.config.ts`）は `src/` の外（リポジトリ直下）に置く。

### 設定

```ts
// orval.config.ts
import { defineConfig } from 'orval'

export default defineConfig({
  api: {
    input: './src/api/openapi.yaml',
    output: {
      target: './src/api/generated/index.ts',
      schemas: './src/api/generated/model',
      client: 'react-query',
      httpClient: 'fetch',
      override: {
        fetch: { includeHttpResponseReturnType: false },
        mutator: { path: './src/api/mutator.ts', name: 'customFetch' }
      }
    }
  }
})
```

* `includeHttpResponseReturnType: false` は必須。既定では、生成された関数が `{ data, status, headers }` を返すため、画面で `data.data` と書くことになる。`false` にすると本文だけが返る。引き換えに、ステータスやヘッダーを画面で使えなくなる（必要なアプリは `true` に戻し、mutator も `{ data, status, headers }` を返す形にする）。
* mutator は JSON をそのまま返す。失敗（`!response.ok`）は `ApiError` を投げる。
* Orval の公式ドキュメントの例は axios 前提で古い。設定は、生成して出力を確かめながら決める。

### エラーの型

* 生成された hook のエラーの型は、既定では `unknown` になる。このままだと `error.message` が型エラーになり、`if (error)` で `data` の型も絞り込めない。
* mutator に `ErrorType` を export して、エラーの型を上書きする。`npm run generate` で再生成すると、生成された hook のエラーの型が `ErrorType<unknown>` になり、`error.message` が使え、`data` も絞り込まれる。

```ts
// src/api/mutator.ts
export class ApiError<Body = unknown> extends Error {
  constructor(
    readonly status: number,
    message: string,
    readonly body?: Body
  ) {
    super(message)
  }
}

export type ErrorType<Body> = ApiError<Body>
```

### 採用理由

* hook まで生成でき、手書きを最小にできる。
* 画面から URL の文字列が消え、関数名の typo をコンパイルで検出できる。
* 8.x で安定している。

### 弱点と補い方

* キャッシュキーの形が生成側で決まり、暗黙になる。
* 補い方は 2 つ。更新で捨てる対象を「操作 → 捨てる対象」の表で明示する。無効化のテストで取りこぼしを検出する。

## 取得と更新の呼び方（TanStack Query + Orval）

### 取得

生成された hook を、画面から直接呼んでよい。URL の文字列もキャッシュキーも画面に出てこないため、手書きの hook で包む理由がない。

```tsx
const { data } = useGetItem(itemId)
```

hook の名前は OpenAPI の `operationId` に由来する。

### 更新

生成された hook を画面から直接呼んでよい。ただし、**更新後にキャッシュの無効化などの処理が要るときだけ**、feature の `hooks/` に包んだ hook を作る。無効化の要らない更新は、包まない。

```tsx
// src/features/items/hooks/use-create-item.ts
export function useCreateItem() {
  const queryClient = useQueryClient()
  return usePostItems({
    mutation: {
      onSuccess: () => {
        // 「操作 → 捨てる対象」の表のとおりに無効化する
        queryClient.invalidateQueries({ queryKey: getGetItemsQueryKey() })
      }
    }
  })
}
```

`useGetItem`・`usePostItems` などの名前は、OpenAPI の `operationId` から決まる例。

包む hook は、生成された hook と同じ名前にできない（`createPost` から `useCreatePost` が生成されるため）。名前は「`<生成された hook の名前>And<やること>`」にする（例: `useCreatePostAndRefresh`。ファイルは `use-create-post-and-refresh.ts`）。

### 無効化を 1 か所にまとめる選択肢

更新が多いアプリは、`QueryClient` の `MutationCache` に共通の `onSuccess` を置き、更新ごとに `meta` で「何を捨てるか」を付ける方式も選べる。画面にもラップ hook にも、無効化のコードを書かなくて済む。更新が少ないうちは、上の包んだ hook で足りる。

### feature の `hooks/` に残るもの

* 無効化などを伴う更新のラップ
* 複数の生成 hook を組み合わせる合成（画面の状態、入力フォーム、派生値）
* 画面の挙動（フォーカス時の再取得など）
