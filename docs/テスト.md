# テスト

Expo アプリのテスト方針。置き場は[フォルダ構成](./フォルダ構成.md)、使うライブラリは[選定ライブラリ](./選定ライブラリ.md)が持つ。本資料は「何をどのテストで確かめるか」を扱う。

## 方針

| 層                       | 採用                | 対象                                                             | 置き場                           |
| ------------------------ | ------------------- | ---------------------------------------------------------------- | -------------------------------- |
| 単体テスト               | Vitest（node 環境） | 純粋なロジック（入力と出力だけで完結する関数）                   | 対象の隣に `*.test.ts`           |
| E2E テスト               | Playwright          | Web 版（react-native-web）の画面操作。利用者が達成する一連の流れ | リポジトリ直下の `e2e/*.spec.ts` |
| 画面のレンダリングテスト | **書かない**        |                                                                  |                                  |
| 見た目の確認             | 人間が目視          |                                                                  |                                  |

画面のレンダリングテストは書かない。セットアップが複雑で壊れやすく、確かめたい「見た目が正しいか」は、目視のほうが確実なため。

## 単体テスト（Vitest）

* 対象は `src/` 配下の `*.test.ts`。node 環境で動くため、`react-native` を import するファイルは対象にならない。
* **計算・検証などの判断は、副作用のない純粋な関数に寄せて書く**（検証のスキーマは feature の `schemas/`、それ以外は `utils/` に置く）。画面や hook の中に判断を埋め込むと、テストで確かめられない。
* 外部の入出力（ネットワーク・現在時刻・乱数）に触れる必要があるときは、引数で受け取る。
* 1 テスト 1 つの振る舞い。異常系を先に書く。
* スクリプトは `test`（1 回実行）と `test:watch`。設定は `vitest.config.mts`（`@` を `src` に解決する alias を含める）。ESM の構文で書くため、拡張子は `.mts`（`.ts` だと CommonJS として読まれ、警告が出る）。`__dirname` は使えないので、`import.meta.dirname` を使う。

## E2E テスト（Playwright）

* iOS・Android・Web は同じコードで動く（Expo Router と react-native-web）ので、画面の動作の大半は Web でも確かめられる。E2E は Web を対象にする。
* Playwright の `webServer` で Expo の Web 開発サーバーを起動してから実行する。**開発用（`npm run web`、8081）とは別のポートで起動し、起動済みのサーバーは再利用しない**（`reuseExistingServer: false`）。再利用すると、接続先が実 API の開発サーバーに当たり、API の差し替えが効かず失敗する。
* 画面の要素は `testID` で指定する。react-native-web は `testID` を `data-testid` として出力するので、`getByTestId` がそのまま使える。ロールや表示文言で取れる要素は、それを優先してよい。
* 利用者が何かを達成する流れや、守られるべき制約を単位にしてテストを切る。画面を 1 つずつなぞるだけのテストは書かない。
* 正常系だけでなく、失敗や不正な入力の流れも含める。
* API のレスポンスは、Playwright の `page.route` で差し替えられる。実物のバックエンドに当てるか、差し替えるかは、バックエンドの有無に合わせてアプリが決める。
* スクリプトは `e2e`。設定は `playwright.config.ts`。

### 初回の準備

初回（と Playwright を更新したあと）に、ブラウザを入れる: `npx playwright install chromium`（約 300MB）。Playwright は、バージョンごとに対応するブラウザの版が決まっている。入っていないと、全件が `Executable doesn't exist at …` で失敗する。

### API の差し替え

実 API に届かせず、`page.route` で応答する。

* **接続先のホストに依存しない。** `.env.local` があると、その値が `webServer.env` で渡した接続先より優先される（SDK 58 で確認。開発サーバーの `EXPO_PUBLIC_*` は、シェルの環境変数より `.env.local` が勝つ）。そのため、「アプリ自身（`localhost`）以外へ出る、API のパスへのリクエスト」を判定する関数を `page.route` に渡して差し替える。ホストを決め打ちにすると、`.env.local` がある環境で全件が失敗する。
* `webServer.env` の接続先（例: `http://api.test`）は、`.env.local` が無い環境（CI など）で、実 API に届かないようにするために置く。
* アプリ（`localhost`）と API はオリジンが違うので、ブラウザが先に送るプリフライト（`OPTIONS`）にも、204 と CORS のヘッダー（`access-control-allow-origin` など）で応答する。
* 差し替えは、`e2e/mock-api.ts`（`mockApi`）に集め、複数の `*.spec.ts` から使う。画面ごとの `spec` に、同じ差し替えを書き写さない。

### 認証の流れ

認証のある画面（ホームなど）は、ログインしないと入れない。`mockApi` は、既定で**ログイン済み**（`/auth/me` が 200）にして、投稿などの画面のテストが、ログインを経ずに始まるようにしてある。ログインの流れを確かめるテストは、`mockApi(page, { loggedIn: false })` で始める。

* Web の認証は Cookie で、ブラウザが送る。差し替えでは、Cookie の代わりに、`mockApi` の中の「ログイン済みか」で `/auth/me` の応答（200 / 401）を決める。ログインの API（`/auth/login`）が成功すると、ログイン済みになる。
* 認証付きの API は、資格情報つき（`credentials: 'include'`）で呼ばれる。このとき CORS の応答は、`access-control-allow-origin` に `*` を使えない。リクエストの `origin` をそのまま返し、`access-control-allow-credentials: true` を付ける。
* `e2e/auth.spec.ts` のテスト: ログインしてホームへ入る、パスワードが違うとエラーが出る、未ログインで URL を直接開くとログインに戻される、ログアウトでログインに戻る。
* 画像は実物に取りに行かない。画像の URL へのリクエストにも、1 ピクセルの PNG で応答する。
* Stack は前の画面を残すので、詳細を開いても、一覧の文字が画面に残る。文字で探す（`getByText`）と、複数に一致することがある。一致が増えたら、`exact` や、ロール・`testID` で絞る。

### 失敗の流れ

TanStack Query は、失敗すると既定で 3 回まで自動で再試行する（1・2・4 秒待つ）。エラー表示までに約 7 秒かかり、1 回だけ失敗させるモックでは、エラー表示が一度も出ない。

* 失敗させ続けて、エラー表示を長めに待つ（15 秒）。
* 復旧させてから「再試行」を押す。
* 実行の成果物（`test-results/`、`playwright-report/`）は `.gitignore` に入れる。

### E2E で確かめられないこと

Playwright は Web 版しか動かせない。権限ダイアログ、ジェスチャ、`expo-secure-store` など、ネイティブ固有の動きは対象外になる。Web でも、Cookie が実際に送られるか（アプリと API が同じサイトか）は、差し替えでは確かめられない（[認証](./認証.md#web-の-cookie-が送られる条件)）。これらを自動で確かめたいアプリは、Maestro などをそのアプリで追加する（テンプレートには含めない）。

## テストを書かないもの

* 生成されたコード（`src/api/generated/`）
* 分岐のない値の詰め替え・受け渡し
* ライブラリ自体の動作
* 画面の見た目（人間が目視で確かめる）
