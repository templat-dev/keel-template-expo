# フォルダ構成

Expo アプリのフォルダ構成ルール。画面本体・hooks を機能単位（`features/<name>/`）にまとめる。

本資料は「どこに置くか」だけを扱う。使うライブラリと、その使い方は[選定ライブラリ](./選定ライブラリ.md)が持つ。

## 全体像

```
├── src/
│   ├── app/                       # Expo Router の route 専用。ここのファイルは全て route になる
│   │   ├── _layout.tsx
│   │   ├── login.tsx              #   features/<name>/screens の画面を描画するだけ
│   │   ├── (tabs)/                #   タブ。_layout.tsx と、画面ごとの route
│   │   └── posts/                 #   動的 route（[id].tsx）など
│   ├── features/                  # 機能単位のまとまり（粗く切る）
│   │   ├── auth/                  #   ログイン画面、ログイン後の処理、起動時の復元
│   │   ├── settings/
│   │   └── posts/
│   │       ├── screens/           #   画面本体（複数可）。route から描画される
│   │       ├── components/        #   posts 内だけで使う component
│   │       ├── hooks/             #   posts 内だけで使う hooks
│   │       ├── schemas/           #   posts 内だけで使う Zod スキーマ（フォームなど）+ 同居する test
│   │       └── utils/             #   posts 内だけで使う純粋な helper + 同居する test
│   ├── api/                       # API 契約・クライアント・生成物。生成物は手で編集しない
│   │   ├── openapi.yaml           #   API 契約（生成の入力）
│   │   ├── generated/
│   │   ├── mutator.ts
│   │   ├── query-client.ts
│   │   ├── auth-state.ts          #   認証状態の atom
│   │   ├── token-storage.ts       #   認証トークンの保存（ネイティブ）
│   │   └── token-storage.web.ts   #   同上（Web。何もしない）
│   ├── components/                # 複数 feature で使う共通 UI。種類ごとのフォルダに分ける
│   │   ├── dialog/                #   ダイアログ（dialog.tsx。確認・案内など、増えたらここに足す）
│   │   ├── form/                  #   入力（text-field.tsx。選択・チェックなどは、2 つ目の feature で必要になったら足す）
│   │   ├── image/                 #   画像（avatar.tsx。expo-image を使う）
│   │   ├── layout/                #   画面の外枠と戻るボタン（screen.tsx はセーフエリアを持つ。content.tsx は内容の最大幅。back-button.tsx）
│   │   └── screen-state/          #   画面の状態（loading.tsx・error-view.tsx・empty-view.tsx）
│   ├── hooks/                     # 複数 feature で使う共通 hooks（use-theme.ts、use-current-user.ts など）
│   ├── schemas/                   # 複数 feature で使う Zod スキーマ + 同居する test（2 つ目の feature で使うようになったら足す）
│   ├── utils/                     # 純粋な helper + 同居する test（format-full-name.ts など）
│   ├── constants.ts
│   ├── theme.ts                   # 色の定義（ライト / ダーク）とナビゲーションのテーマ
│   └── global.css                 # Tailwind のエントリ（NativeWind）
├── e2e/                           # Playwright の E2E テスト（*.spec.ts）と、API の差し替え（mock-api.ts）
├── .github/workflows/ci.yml       # CI（GitHub Actions）
├── .env.example                   # 環境変数の見本（コミット）
├── .env.local                     # 各自の端末固有の値（git 管理外。.env.example をコピーして作る）
├── .env.development               # 開発時の値（環境ごとに違うときだけ書く）
├── .env.production                # 本番ビルドの値（同上）
├── .nvmrc                         # Node のバージョン
├── .prettierrc                    # Prettier の設定（Standard Style 準拠）
├── .prettierignore                # Prettier の対象外（生成物）
├── app.json
├── babel.config.js                # NativeWind の Babel の設定
├── eas.json
├── eslint.config.js
├── metro.config.js                # NativeWind の Metro の設定
├── nativewind-env.d.ts            # className の型
├── orval.config.ts
├── package.json
├── playwright.config.ts
├── tailwind.config.js             # Tailwind の設定（ダークモードは class）
├── tsconfig.json
├── vitest.config.mts
└── CLAUDE.md
```

この図は、テンプレートにあるものだけを載せている。`assets/`（アイコン・画像）、`scripts/`、platform 別の layout（`_layout.web.tsx`）、`.env.local` などは、必要になったアプリが足す。

tsconfig の `@/*` は `./src/*` を指す（例: `@/features/posts/screens/post-list`）。

## 何をどこに置くか（早見表）

置き場に迷ったら、まず、この表を引く。コードの種類ごとに、置き場と基準を定めている。**基準が既存のルールにあるものは、ルールへのリンクだけを書く。** 表にしか基準がないものは、この表が唯一の定義元。「必要になったとき作る」と書いたものは、サンプルには無い。必要になるまで作らない。

### 画面と UI

| 種類 | 置き場 | 基準・補足 |
| --- | --- | --- |
| route、`_layout` | `src/app/` | [ルール 1](#1-srcapp-は-route-専用) |
| 画面本体 | `features/<name>/screens/` | route から描画されるもの。見本は `post-list.tsx` |
| その feature だけで使う部品 | `features/<name>/components/` | **データを取得する部品でもよい**（見本: `post-list-header.tsx` はユーザーを取得する）。1 つのファイルの中でしか使わない小さな部品は、そのファイルに書く（見本: `post-list.tsx` の `PostListBody`）。他のファイルから使うか、ファイルが長くなったら切り出す |
| 複数の feature で使う UI | `src/components/<種類>/` | [ルール 5](#5-共通フォルダ) |
| 自作の Provider（Context） | `_layout.tsx` に直接書く | ライブラリが要求する Provider と同じ。長くなったら `src/providers/` に切り出す（必要になったとき作る）。Context に載せてよい値は[クライアント状態](./選定ライブラリ.md#クライアント状態jotai) |
| 色・テーマ | `src/theme.ts` | [テーマ](./選定ライブラリ.md#テーマsrcthemets) |
| 画像・フォントなどの静的ファイル | `assets/`（`src/` の外）に、種類ごとのサブフォルダ（`images/`・`fonts/`） | 必要になったとき作る。ネットワークから取る画像は置かない |

### ロジックと状態

| 種類 | 置き場 | 基準・補足 |
| --- | --- | --- |
| React に依存する処理 | `hooks/`（feature 専用は `features/<name>/hooks/`、複数の feature で使うなら `src/hooks/`） | hook を呼ぶ（`useState`・`useRouter` など）、または `react-native` を import する。1 ファイル 1 hook で、名前は `use-` で始める。**1 つの画面でしか使わない短い処理は、画面の中に書く。** 2 つ以上の画面で使う、または名前を付けて切り出したい挙動（合成、無効化つきの更新など）は hook にする |
| React に依存しない処理 | `utils/` | 入出力だけで完結する純粋な関数。単体テストの対象（[テスト](./テスト.md#単体テストvitest)） |
| 入力の検証と変換 | `schemas/` | Zod のスキーマと、そこから導く型・変換の関数（[画面の書き方](./画面の書き方.md#フォーム)） |
| 取得と更新 | 生成された hook を、画面から直接呼ぶ | 無効化が要る更新のラップと、複数の hook の合成は、feature の `hooks/`（[取得と更新の呼び方](./選定ライブラリ.md#取得と更新の呼び方tanstack-query--orval)） |
| クライアント状態（atom） | 使うファイルに直接書く | 複数の feature で使うようになったら昇格（[ルール 3](#3-昇格ルール共通フォルダへの移動)） |
| 認証状態・トークンの保存 | `src/api/` | mutator が使うため（[認証](./認証.md#置き場)） |
| 外部 SDK・ネイティブ機能のラッパー（通知、カメラ、分析など） | `src/lib/<機能>.ts` | 必要になったとき作る。`src/api/` は、API の通信と認証だけを置く。ネイティブ専用のものは Web で import できないので、[ルール 6](#6-platform-別コード)に従ってファイルを分ける |

### 型・定数・テスト

| 種類 | 置き場 | 基準・補足 |
| --- | --- | --- |
| 型 | 使うファイルの中 → feature の `types.ts` → `src/types/` | 1 つのファイルでしか使わない型は、そのファイルに書く。複数のファイルで使うなら、feature の `types.ts`。2 つの feature で使うようになったら `src/types/`（どちらも、必要になったとき作る）。API の型は生成されたものを使う（[4 状態](./画面の書き方.md#データ取得を伴う画面の-4-状態)） |
| 定数 | 使うファイルの先頭 → feature の `constants.ts` → `src/constants.ts` | 1 つのファイルでしか使わない定数は、そのファイルの先頭に書く（見本: `post-list.tsx` の `KEYWORDS`）。複数のファイルで使うなら、feature の `constants.ts`（必要になったとき作る）。2 つの feature で使うようになったら `src/constants.ts`（環境変数も、ここで読む。[環境変数](./開発環境と設定.md#書き方)） |
| 単体テスト | 対象の隣 | [ルール 7](#7-style-と-test-は同居) |
| E2E テストと、その API の差し替え | `e2e/` | `*.spec.ts` と `mock-api.ts`（[テスト](./テスト.md#api-の差し替え)） |
| テストで使うデータ | そのテストの中 | 複数のテストで共有するようになったら、対象の隣に、データを書いたファイルを置く（必要になったとき作る） |

## ルール

### 1. src/app は route 専用

ここには、ファイル名・パス・ナビゲーション構造に結びつくものだけを置く。置いたファイルは全て route として扱われるため、それ以外は置かない。

置くもの

* route ファイル（URL パラメータの読み取りと、文脈なしで決まる型変換・検証を含む）
* `_layout`（Stack・Tabs の構成、画面名の一覧、画面タイトル、認証ガード、ライブラリが要求する Provider、`unstable_settings`）と platform 別 layout
* 純粋なリダイレクト、`+not-found`、`ErrorBoundary`、`SuspenseFallback`、`+native-intent` などの規約ファイル・export

置かないもの（画面本体の側に置く）

* 画面の挙動（`router.push` などの遷移、`useFocusEffect`、データに依存するヘッダー）
* 実行時のデータが要る解釈（有効な範囲内か、権限があるか）
* レイアウトの見た目の細部（タブバーの寸法など）。長くなったら画面名の一覧を残して外に出す

route は薄く保つ

* route 側で行うのは、URL パラメータの読み取りと、文脈なしで決まる変換・検証（`Number(id)`、許可された値かの確認）まで。
* 不正な値のときの表示（エラー表示、not-found、リダイレクト）も route が決める。
* 画面本体には、型付きの値を props で渡す。

```tsx
// src/app/item/[id].tsx
import { useLocalSearchParams } from 'expo-router'
import { ItemDetail } from '@/features/items/screens/item-detail'

export default function ItemDetailRoute() {
  const { id } = useLocalSearchParams<{ id: string }>()
  return <ItemDetail itemId={Number(id)} />
}
```

パラメータのない画面は 1 行にできる。

```tsx
export { PostList as default } from '@/features/posts/screens/post-list'
```

画面タイトル

* 既定は `_layout` の `<Stack.Screen name="..." options={{ title }} />` に直接書く。読み込み中や未ログインのような早期 return の状態でも効く。
* 複数の消費者（ネイティブと Web の layout など）が同じ一覧を読むようになったら、表に切り出す。切り出したら、route の一覧と突き合わせるテストを一緒に置く。
* 取得したデータに依存するタイトル（商品名など）は、layout に既定の題を持たせ、読み込み後に画面本体の `Stack.Screen` で上書きする。

認証ガード

* 「どの URL に誰が入れるか」は `_layout` の `Stack.Protected` / `Tabs.Protected` で書く。

動的 route の下に子の route（詳細の下の編集など）を置くとき

* 動的 route は `[id]/index.tsx` にし、子の route を `[id]/edit.tsx` として並べる。
* `_layout` の `Stack.Screen` の名前は `items/[id]/index`・`items/[id]/edit`、`href` は `{ pathname: '/items/[id]/edit', params: { id } }` になる。

typed routes

* `app.json` の `experiments.typedRoutes` を有効にし、`href` はキャストせず型付きで渡す。

### 2. features/<name>/ は機能単位

画面本体、その機能専用の `components/`・`hooks/`・`schemas/`・`utils/` を同居させる。

* 画面本体は `screens/` に置く。1 つの feature に複数の画面を置いてよい（例: 一覧・詳細・確認）。
* 画面が長くなったら、一部を `components/` に切り出す（例: `features/posts/components/post-list-header.tsx`、`features/settings/components/account-section.tsx`）。その feature の中だけで使う部品を置く。2 つ目の feature で使うようになったら、昇格ルールに従う。
* フォームなどの検証のスキーマ（Zod）と、そこから導く型・変換の関数は `schemas/` に置く。
* 計算などの純粋なロジックは `utils/` に置く（副作用を持たない関数。単体テストの対象）。
* 最初に迷ったら、まず `features/<name>/` に置く。
* feature は業務のまとまりで切る。画面ごとや API リソースごとに細かく切らない。同じ部品やデータを使う機能は、同じ feature にまとめる（別にすると、部品を共通フォルダへ昇格させる必要が出る。例: レシピの一覧とお気に入りの一覧）。

### 3. 昇格ルール（共通フォルダへの移動）

* 最初は全て `features/<name>/` 配下に置く。
* 2 つ目の feature で同じものが必要になった時点で、種類に応じて共通フォルダへ移す（例: 姓名の整形 `formatFullName` は、ホームの挨拶と設定のアカウントで使うので `src/utils/` にある）。
  * UI → `src/components/`
  * hooks → `src/hooks/`
  * Zod スキーマ → `src/schemas/`
  * 純粋な helper → `src/utils/`
* 2 つ目が出る前に、先回りして共通化しない。
* `hooks/`・`schemas/`・`utils/` のものが、使うのが 1 つの feature だけになったら、その feature に戻してよい（置き場は「今どこで使われているか」で決める）。`components/` は、汎用の UI（`Dialog`・`TextField`・`Avatar` など）で、使う数ではなく性質で決めるので、戻さない。
* 状態管理の atom は、専用のフォルダを作らない。使うファイル（hooks や components）に直接書いてよい。複数の feature で使うようになったら、上の昇格ルールに従う。

### 4. feature 間の依存

* feature 同士は直接 import しない。別の feature のものが必要になったら、共通フォルダへ昇格させてから使う（昇格先は 3 を参照）

### 5. 共通フォルダ

* `components/`: 複数 feature で使う汎用 UI のみ。**種類ごとのフォルダ（`dialog/`・`form/`・`screen-state/` など）に分ける。** 同じ種類のものが増えやすいため（ダイアログなら、確認・案内・入力つきなど）。
  * named export は 1 ファイル 1 つ（例: `dialog/confirm-dialog.tsx`）。
  * import は、フォルダまで含めたファイルのパスで書く（`@/components/dialog/dialog`）。`index.ts` で再 export しない（どのファイルを使っているかが追いにくくなる）。
  * 種類が決まらない 1 つだけの部品は、`components/` 直下に置いてよい。同じ種類が 2 つ目になった時点で、フォルダに分ける。
* 肥大化した component は folder 化して `index.tsx` を root にし、private な sub-component を同居させる（import path は変わらない）。
* `hooks/`・`schemas/`・`utils/`: 複数 feature で使うものだけを置く。

### 6. platform 別コード

* 小さな差分は `Platform.select` / `Platform.OS` で書く。
* 大きな差分はファイルを分ける（`bar-chart.tsx` + `bar-chart.web.tsx`）。import は拡張子なしで書く（`@/components/chart/bar-chart`）。
* 対応する拡張子は `.ios` `.android` `.native` `.web`。
* 全 variant で props を揃える。
* 拡張子なしの default ファイルは必須（単一 platform 専用の component なら no-op にする）。
* ネイティブ専用のモジュール（例: `expo-secure-store`）は、Web で import しただけでエラーになることがある。そのモジュールを使う処理は、ネイティブ用の `foo.ts` と Web 用の `foo.web.ts` に分け、どちらも同じ名前・同じ引数の関数を export する。Web 用は、Web の代わりの実装（または何もしない実装）にする。型は `foo.ts` が検査する。
  * 見本は `src/api/token-storage.ts` と `token-storage.web.ts`（`get`・`set`・`clear`。[認証](./認証.md#置き場)）。

### 7. style と test は同居

* style: `className` に書き、`StyleSheet` や `.styles` ファイルは作らない（書き方は[選定ライブラリ](./選定ライブラリ.md#書き方)）。
* test: 対象ファイルの隣に置く（`format-date.test.ts`）。`__tests__/` は作らない。E2E テストだけは、リポジトリ直下の `e2e/` に置く（方針は[テスト](./テスト.md)）。

### 8. その他

* ファイル名は kebab-case に統一する。
* `app.json`（または `app.config.ts`）、`babel.config.js`、`metro.config.js`、`tailwind.config.js`、`nativewind-env.d.ts`、`eas.json`、`eslint.config.js`、`.prettierrc`、`orval.config.ts`、`package.json`、`tsconfig.json`、`vitest.config.mts`、`playwright.config.ts`、`.env*`、`assets/`、`scripts/`、`e2e/` は `src/` の外に置く。
* `.env*` はプロジェクトのルートに置く（Expo CLI が探すのはルートだけ）。使い方は[開発環境と設定](./開発環境と設定.md#環境変数)。
* `CLAUDE.md` / `AGENTS.md` はリポジトリ直下、project skills は `.claude/` 配下。
* `.gitignore` は、Expo 公式テンプレート（`expo-template-default`）のものをもとに、`.idea/`・`test-results/`・`playwright-report/` を足している。
